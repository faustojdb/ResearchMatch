## 1. NEED-04 — File Sharing (Level 4 Metadata Registry)

### Contexto
Despues de bilateral Level 3 reveals (ambos investigadores compartieron sus Research Commits completos), el siguiente paso natural es compartir archivos de soporte: codigo, scripts, notebooks, datos. La tabla `shared_files` existia scaffolded desde v2.4.0 pero sin codigo que la usara. NEED-04 la activa como **registro de metadata** — los investigadores registran metadata del archivo (path, hash, descripcion) e intercambian el contenido real fuera de banda.

**Modelo de consentimiento**: Bilateral Level 3 es el gate. No se necesita consent per-file — si ya compartiste tu commit completo, compartir archivos es una escalacion natural.

### Infraestructura preexistente
- `shared_files` tabla scaffolded (id, team_id, consent_id nullable, shared_by, file_path, file_hash, origin_user_id, shared_at)
- `reveal_consents` soporta `level IN (3, 4)` — listo
- `audit_log` tiene `file_shared` y `file_accessed` en CHECK constraint — listo
- Indices: `idx_shared_files_team`, `idx_shared_files_origin` — listos

## 2. Cambios implementados

### 2a. Schema migration
```sql
ALTER TABLE shared_files ADD COLUMN description TEXT;
```
Tambien agregado al CREATE TABLE para nuevas instalaciones. Patron estandar `try/except OperationalError`.

### 2b. Constantes nuevas
```python
MAX_SHARED_FILES_PER_TEAM = 50
MAX_FILE_PATH_LENGTH = 500
MAX_FILE_DESCRIPTION_LENGTH = 500
```

### 2c. Modelos Pydantic nuevos

| Modelo | Campos | Proposito |
|--------|--------|-----------|
| `ShareFileInput` | `team_id`, `file_path` (1-500), `file_hash` (opt), `description` (opt, max 500) | Registrar archivo |
| `SharedFilesInput` | `team_id` | Listar archivos del team |

Ambos con `extra="forbid"` y `str_strip_whitespace=True`.

### 2d. Tool: `research_match_share_file`

**Validaciones (en orden):**
1. Usuario registrado
2. Miembro del team
3. **Bilateral Level 3 gate**: ambos miembros deben tener >=1 reveal aprobado en cada direccion
4. Limite: `MAX_SHARED_FILES_PER_TEAM` (50)
5. Dedup: `(team_id, shared_by, file_path)` — retorna `already_shared` con file_id existente

**Accion:**
- INSERT en `shared_files` con `consent_id=NULL`, `origin_user_id = user["id"]`
- `_write_audit_log(action='file_shared')` con details de path/hash/description

**Annotations:** `readOnlyHint=False, idempotentHint=True`

### 2e. Tool: `research_match_shared_files`

**Validaciones:** usuario registrado, miembro del team.

**Accion:**
- SELECT shared_files JOIN users para pseudonyms, ORDER BY shared_at DESC
- `_write_audit_log(action='file_accessed')` solo si hay archivos
- Incluye `is_yours` flag por archivo, `by_member` summary

**Annotations:** `readOnlyHint=True, idempotentHint=True`

## 4. Decisiones de diseno

1. **Metadata registry, no file server** — path + hash + descripcion. Contenido via email/repo.
2. **Bilateral L3 como gate** — no consent per-file. Si compartiste tu commit, archivos es escalacion natural.
3. **`consent_id = NULL`** — columna existe para extension futura, no se usa en v1.
4. **`origin_user_id = shared_by`** siempre — solo puedes compartir tus propios archivos.
5. **Dedup por `(team_id, shared_by, file_path)`** — idempotente, retorna ID existente.
6. **No afecta `_compute_license`** — archivos no cambian tipo de licencia en v1.
