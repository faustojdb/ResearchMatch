## 1. analyze_repo.py — Analizador de Repositorios

### Que es
Script single-file (~1200 LOC) que analiza cualquier repo local: estructura de archivos, LOC por lenguaje, dependencias, tools MCP (JS SDK + Python FastMCP), y opcionalmente compara contra un proyecto de referencia para generar mejoras adoptables priorizadas.

### Arquitectura (5 capas)

| Capa | Funcion | Metodos clave |
|------|---------|---------------|
| Layer 1: Generic | File tree, LOC, deps, git, README | `analyze_file_tree()`, `analyze_dependencies()`, `analyze_git()`, `analyze_readme()` |
| Layer 2: MCP | Framework detection, tool extraction, annotations | `detect_mcp_framework()`, `extract_tools_js()`, `extract_tools_python()`, `detect_mcp_extras()` |
| Layer 3: Comparison | Set diff, annotation gaps, adoptable improvements | `compare_tool_lists()`, `_find_similar_tools()` |
| Layer 4: Originality | Map repo metadata a OriginalityEvaluator | `map_repo_to_commit_data()`, `score_originality()` |
| Layer 5: Output | Text con bar charts o JSON | `format_text()`, `format_json()` |

### CLI
```bash
python3 analyze_repo.py /path/to/repo                          # basico
python3 analyze_repo.py /path/to/repo --mcp                    # con tools MCP
python3 analyze_repo.py /path/to/repo --reference /otro --mcp  # comparacion
python3 analyze_repo.py /path/to/repo --score                  # originalidad
python3 analyze_repo.py /path/to/repo --json                   # output JSON
```

### Extraccion de tools MCP
- **JS SDK**: regex multi-pass sobre `setRequestHandler(ListToolsRequestSchema, ...)` con brace-balancing para extraer cada tool object
- **Python FastMCP**: regex sobre `@mcp.tool(` / `@*.tool(` con paren-balancing para extraer name, description, annotations del decorador

### Data models (dataclasses stdlib)
- `RepoMetadata` — path, name, readme, git info
- `FileStats` — files/dirs count, files_by_extension, loc_by_language, largest_files
- `DependencyInfo` — package.json, requirements.txt, pyproject.toml, detected_framework
- `MCPToolDef` — name, description, source_file, source_line, params, annotations
- `MCPAnalysis` — framework, tool_count, annotation_coverage, tools, resources/prompts/transport
- `ComparisonResult` — tools only_in_target/reference/both, annotation_gaps, adoptable_improvements
- `AnalysisReport` — repo, files, deps, mcp, comparison, originality

### Bugs encontrados y corregidos
- Git date format: `--format=%Y-%m-%d` no funciona en git log (no es un format specifier valido). Fix: `--format=%ad --date=short`
- Dependency scan: package.json solo en root no detectaba WhatsappPlugin (tiene package.json en `servers/`). Fix: scan subdirectorios inmediatos tambien

### Verificacion (6 tests pasados)
1. `analyze_repo.py /mnt/d/cowork/WhatsappPlugin` — 25 files, 3 langs, git OK
2. `--mcp` WhatsappPlugin — 19 tools JS, 100% annotations, stdio
3. `--mcp` ResearchMatch — 13 tools Python FastMCP, 69% annotations, sse, resources+prompts
4. `--reference` cross-framework — 19 vs 13 unique, annotation gap HIGH
5. `--score` — graceful error (mcp package not installed), funciona con deps
6. `--json` — valid JSON con todas las estructuras anidadas

## 3. Manifesto de la Capa de Colaboracion

### Archivo
`sessions/2026-02-16_manifesto-collaboration-layer.md`

### El problema central
Despues de `find_collaborators → send_request → respond_request(accept) → team creado`, hay un vacio. No existe infraestructura para compartir trabajo, comunicarse, ni proteger IP.

### Estado actual del flujo post-match
- Teams: se crean con `joint-equal` hardcoded, campos `repository_url` y `contribution_percentage` sin usar
- Rating: funciona completo (anonimo anti-retaliacion, abuse detection, reputation engine)
- Sharing: no existe
- Tickets: no existe
- Licensing: hardcoded, no configurable
- Audit: no existe

### 6 NEEDs definidas

#### NEED-01: Sistema de Tickets / Necesidades (reemplaza al chat)
- Principio: sin conversacion libre, solo tickets estructurados ("pull requests intelectuales")
- Tipos: `need_help`, `can_offer`, `warning`, `question`
- Areas: `theory`, `code`, `data`, `review`, `infrastructure`
- Status: `open` → `in_progress` → `resolved` / `wont_fix`
- Tickets resueltos alimentan rating automaticamente
- Limite de tickets abiertos simultaneos

#### NEED-02: Reveal Progresivo (4 niveles)
- **Nivel 1 — Indice**: tags + objetivo hasheado (automatico al publicar)
- **Nivel 2 — Candidato**: scores OT/OFC + semaforo (automatico en match)
- **Nivel 3 — Detalle**: commit completo desencriptado (aprobacion MUTUA)
- **Nivel 4 — Codigo**: archivos seleccionados (seleccion manual, archivo por archivo)

Tablas SQL nuevas:
```sql
reveal_consents (id, team_id, level, requester_id, approver_id, status, resource_type, resource_ref)
shared_files (id, team_id, consent_id, shared_by, file_path, file_hash, shared_at)
```

#### NEED-03: Licenciamiento Automatico
4 tipos: `joint-equal` (50/50), `joint-weighted` (proporcional a tickets resueltos), `advisory-only` (solo consulta), `time-limited` (acceso temporal)
- Se genera automaticamente al primer reveal nivel 3+
- El usuario NO negocia manualmente

#### NEED-04: Control de Re-sharing (Propagacion)
- Respuesta: NO se permite re-compartir. Por diseno.
- `origin_user_id` inmutable en todo contenido compartido
- Violacion → pierde TODOS los derechos + rating honestidad=1 automatico
- Deterrent MAD: el violador pierde tambien derechos sobre su propio trabajo compartido
- `audit_log` tabla inmutable para trail completo

```sql
audit_log (id, team_id, actor_id, action, resource_ref, details, ip_hash, created_at)
```

#### NEED-05: 9 Tools MCP nuevos
```
research_match_needs_create     — Crear ticket
research_match_needs_list       — Listar tickets del team
research_match_needs_resolve    — Resolver ticket
research_match_reveal_request   — Solicitar reveal nivel 3/4
research_match_reveal_approve   — Aprobar/denegar reveal
research_match_shared_files     — Listar archivos compartidos
research_match_share_file       — Compartir archivo (nivel 4)
research_match_team_license     — Ver licencia del team
research_match_audit_log        — Ver trail de auditoria
```

#### NEED-06: cold_search siempre dual + deep_search futuro
- **Fix inmediato**: cold_search busca SIEMPRE en ambas fuentes con limite completo (ya aplicado)
- **Futuro (deep_search)**: clonar repo → analyze_repo.py → comparacion automatizada

### Solidez del planteo
| Componente | Nivel |
|-----------|-------|
| Tickets/needs | Especulativo |
| Reveal progresivo | Especulativo |
| Licenciamiento auto | Especulativo |

### Analisis de repos clonados

**lharries/whatsapp-mcp** (competidor principal, ~2K stars):
- Go bridge + Python FastMCP + SQLite
- Nuestro analizador detecto: 1,348 LOC Go + 1,128 LOC Python, framework python-fastmcp
- No extrajo tools (usa patron diferente: funciones registradas programaticamente, no decoradores)
- Conclusion: nuestro WhatsappPlugin lo supera en features (19 vs ~10 tools), tiene Gmail, agente autonomo, image gen, transcripcion

**harche/ProDisco** (progressive disclosure):
- 34,141 LOC TypeScript, framework js-sdk
- Genera tools DINAMICAMENTE (meta-tool que revela operaciones incrementalmente)
- El patron es: exponer un tool "discover" que devuelve sub-tools segun contexto
- Relevante para nuestro reveal progresivo: en vez de exponer todo, exponer segun nivel de consentimiento

**MarcusJellinghaus/mcp_server_filesystem**:
- 6,090 LOC Python, framework python-fastmcp
- Access control: directories allowed/denied, security modes
- Patron "reference projects" (read-only) vs "main project" (read-write)
- Directamente aplicable a nuestro file sharing con consentimiento

**daffidwilde/matching**:
- 5,503 LOC Python puro
- Implementa: Stable Marriage, Hospital-Resident, Stable Roommates, Student Allocation
- Todos usan Gale-Shapley algorithm
- BasePlayer con preferences + BaseGame con solve()/check_stability()
- Adaptable: nuestros researchers son "players", sus OT/OFC profiles definen preferences

**human-AI-complementarity-matching**:
- 2,160 LOC Python, requiere Gurobi (LP solver comercial)
- MWBCM: Maximum Weight Bipartite Capacity Matching
- Greedy fallback: `greedy_max_weighted_matching()` sin Gurobi (259 LOC, usable)
- Concepto clave: matching que maximiza complementariedad (no similaridad)
- El "weight" en nuestro caso seria: distancia OT/OFC entre dos researchers

**ragieai/dynamic-fastmcp**:
- Solo 242 LOC core (dynamic_fastmcp.py)
- DynamicTool Protocol: `name()`, `handle_description(ctx)`, `handle_call(*args)`
- DynamicToolManager extiende ToolManager con `_dynamic_tools` dict
- DynamicFastMCP extiende FastMCP, overridea `list_tools()` y `tool()` decorator
- Patron clave: tools cuya descripcion cambia segun contexto del request

## 5. Fix aplicado: cold_search dual obligatorio

### Problema
El cold_search repartia slots entre fuentes: si pedias 10 resultados, daba 5 internos + 5 GitHub. Priorizaba la DB interna.

### Fix (research_match_server.py, linea 2298)
Antes:
```python
internal_limit = max(1, limit // 2)
github_limit = max(1, limit - internal_limit)
# ...
if len(internal_results) < internal_limit:
    github_limit += (internal_limit - len(internal_results))
```

Despues:
```python
# Always search BOTH sources with full limit each.
internal_results = _cold_search_internal(db, query, limit)
github_results = _cold_search_github(query, limit)
```

### Justificacion
Puede haber 1000 repos utiles afuera incluso cuando la DB interna tiene matches. Las fuentes no compiten por slots — ambas aportan valor independiente.
