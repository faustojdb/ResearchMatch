# Session 13 — NEED-08: Git-Verifiable Collaboration Contracts

**Fecha:** 2026-02-16
**Version:** 2.7.0-proforma → 2.8.0-contracts
**Foco:** Contratos de colaboracion verificables por git con confirmacion bilateral

---

## Objetivo

Implementar un sistema de contratos que use **git como blockchain**: el contrato se genera como markdown, ambas partes lo commitean a sus repos, y la eliminacion queda registrada en el historial de git. Disputas se resuelven leyendo commit-by-commit.

## Contexto

El sistema de licencias automaticas (NEED-03) funciona pero no tiene enforcement externo. La insight: git ya es una cadena inmutable para codigo. Si el contrato vive en AMBOS repositorios, queda verificable independientemente de Research Match.

## Cambios Realizados

- `2.7.0-proforma` → `2.8.0-contracts`

### 3. Schema
- **Nueva tabla `collaboration_contracts`** — 18 columnas:
  - `id`, `team_id`, `contract_version`, `license_type`, `contribution_split` (JSON)
  - `contract_content` (markdown completo), `content_hash` (SHA-256)
  - `generated_by`, `generated_at`
  - Slots bilaterales: `confirmation_a_*` y `confirmation_b_*` (user_id, git_hash, repo_url, timestamp)
  - `status`: pending → partial → confirmed / superseded
  - UNIQUE(team_id, contract_version)
- **Migration `research_commits`**: 2 columnas nuevas `git_repo_url TEXT`, `git_commit_hash TEXT`
- **Index**: `idx_contracts_team(team_id, status)`

### 4. Pydantic Models (2 nuevos + 1 actualizado)
- `ExportContractInput(team_id)` — input para generar contrato
- `ConfirmContractInput(team_id, contract_id, git_commit_hash, repo_url?)` — con validator SHA-1
- `SubmitCommitInput` actualizado con `git_repo_url?` y `git_commit_hash?` opcionales + validator

### 5. Helper
- `_generate_contract_content(db, team_id, license_info, contract_version)` → markdown string
  - Header: contract ID, team, fecha, version, format version, license type
  - Parties: pseudonym, role, contribution%, joined, reputation, latest commit (domain, hash, OT/OFC, solidity, git refs)
  - License Terms: tipo, rationale, 4 terms
  - Contribution Split: porcentaje por miembro
  - Collaboration State: reveal state + ticket balance
  - Verification: disclaimer bilateral + nota sobre eliminacion + firma version

### 6. MCP Tools (2 nuevos)
- **`research_match_export_contract`** — genera contrato markdown:
  1. Verifica membership
  2. Computa licencia actual
  3. Auto-incrementa version
  4. Supersede contratos pending/partial anteriores
  5. Genera contenido + SHA-256 hash
  6. INSERT en collaboration_contracts
  7. Audit log: `license_generated` con `trigger=contract_generated`
  8. Retorna: contract_id, version, hash, contenido, suggested_path, instrucciones

- **`research_match_confirm_contract`** — confirma commit en git:
  1. Verifica membership + contrato existe + no superseded/confirmed
  2. Determina slot (A libre → A, ya soy A → idempotente, si no → B)
  3. UPDATE slot con git_hash, repo_url, timestamp
  4. Si ambos slots llenos → status = confirmed
  5. Audit log: `license_generated` con `trigger=contract_confirmed`

### 7. Updates a tools existentes (4)
- **`submit_commit`**: INSERT incluye `git_repo_url`, `git_commit_hash`; response los incluye si presentes
- **`respond_request`**: NEXT STEPS agrega paso (7) para `export_contract`
- **`team_license`**: agrega `contracts_count` (confirmed) y `contract_tip`
- **Health stats**: agrega `contracts` counter

## Flujo de Usuario Completo

```
register → submit_commit(git_repo_url, git_commit_hash) → find_collaborators →
send_request → inbox → respond_request →
[needs + reveals + file_sharing + ratings] →
export_contract → [commit file to repo] → confirm_contract →
[other party does same] → contract CONFIRMED
```

## Decisiones de Diseno

1. **Audit action reutilizada** — Usa `license_generated` con `details.trigger` para distinguir contract_generated/contract_confirmed. Evita migrar CHECK constraint.
2. **On-demand** — Contrato se genera cuando el usuario lo pide, no automaticamente al crear team.
3. **Versioning con supersede** — Cada export crea nueva version, invalida anteriores pending/partial.
4. **Bilateral confirmation** — Dos slots (A, B) en la misma row, idempotente por usuario.
5. **git_ref opcional** — Backward compatible, no rompe commits existentes.
6. **Markdown human-readable** — Renderiza en GitHub, legible sin tools.
